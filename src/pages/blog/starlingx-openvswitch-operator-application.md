StarlingX now offers the OpenvSwitch Operator application, a Kubernetes-native way to deploy and manage Open vSwitch (OVS) instances on worker nodes. Using declarative custom resources, operators can define bridges, ports, and per-node network topologies without manually configuring OVS on each host. <!-- more -->
In this blog post, we will introduce the new `openvswitch` application, explain how it is built, and walk through the main ways to install it and connect traffic into and out of the OVS bridges it manages.

### What is the OpenvSwitch Operator Application?

Open vSwitch is a production-grade, multilayer virtual switch widely used to build software-defined networks. The new OpenvSwitch Operator application (`openvswitch`) brings OVS management into the Kubernetes control loop on StarlingX worker nodes. Instead of configuring switches by hand, you describe the desired state through Custom Resource Definitions (CRDs), and the operator reconciles the running OVS configuration on each node to match.

This declarative, operator-based model fits naturally alongside the rest of the StarlingX platform. The application is packaged and lifecycle-managed like any other StarlingX system application, so it can be uploaded, applied, overridden, and removed with a small set of `system` CLI commands.

One important note about scope: the provided application uses kernel bridging underneath. Because of this, all SR-IOV Virtual Function (VF) configurations must use netdevice drivers. The use of VFIO (DPDK) is not supported with this application.

### How is the Application Built?

The `openvswitch` application is made up of two cooperating components.

**OVS Manager Operator** is a Deployment that runs on control-plane nodes. It watches for OVS custom resources (`OVSBridge`, `OVSPort`, and `OVSNodeConfig`) and reconciles the desired state with the actual OVS configuration on each node through the OVS Agent.

**OVS Agent Operator** is a DaemonSet that runs on every node labeled with `ovs-node=enabled`. Each agent pod contains three containers working together:

- `ovs-agent-operator` — the controller that receives instructions from the OVS Manager and configures the local OVS instance accordingly.
- `ovsdb-server` — the OVS database server that manages the switch configuration database.
- `ovs-vswitchd` — the OVS forwarding daemon that implements the configured bridges and ports.

An init container (`ovs-init`) bootstraps the OVS database when the pod starts.

### The Custom Resource Definitions

The application exposes three CRD types that together describe the OVS topology:

- **`OVSBridge`** defines a bridge with optional Spanning Tree Protocol (STP), MAC aging, and a node selector. A bridge targets all nodes matching a label selector.
- **`OVSPort`** defines a port on a named bridge, including VLAN configuration, STP settings, and optional BFD-enabled interfaces.
- **`OVSNodeConfig`** combines bridge and port definitions for a specific node, allowing per-node customization of the OVS topology. This resource is generated by the OVS Manager and is not intended to be edited directly by the user.

### Installing the Application

Before installing, make sure the target worker nodes carry the `ovs-node=enabled` label. The OVS Agent DaemonSet uses this label as a node selector to decide where to schedule its pods, so at least one host must be labeled before you apply the application. If no hosts have the label, the DaemonSet will not schedule any pods.

```
~(keystone_admin)]$ system host-label-assign <hostname> ovs-node=enabled
~(keystone_admin)]$ system application-upload openvswitch
~(keystone_admin)]$ system application-apply openvswitch
```

The application supports Helm overrides for both the `ovs-agent` and `ovs-manager` charts, set with `system helm-override-update`. Overrides let you attach additional interfaces to the OVS pod, tune resource requests and limits (including SR-IOV resource names), adjust health and status host ports, set OVS log levels, and enable host access. For example, to attach SR-IOV interfaces:

```
~(keystone_admin)]$ system helm-override-update openvswitch ovs-agent openvswitch \
   --set ovsAgent.networks='{"name":"ovs-bridge1"\,"interface":"port1"}\,{"name":"ovs-bridge2"\,"interface":"port2"}' \
   --set ovsAgent.resources.requests.intel\\.com/pci_sriov_net_ovs_bridge1='1' \
   --set ovsAgent.resources.limits.intel\\.com/pci_sriov_net_ovs_bridge1='1'
```

For more complex overrides you can pass a YAML file with `--values /path/to/overrides.yaml`. Any referenced NetworkAttachmentDefinitions (NADs) must be created before applying, and after updating overrides you re-apply the application with `system application-apply openvswitch`.

Uninstalling is equally straightforward:

```
~(keystone_admin)]$ system application-remove openvswitch
~(keystone_admin)]$ system application-delete openvswitch
```

During removal, an application lifecycle hook automatically cleans up the OVS webhook configurations and removes finalizers from OVS custom resources, so resource deletion is not blocked.

### Connecting Traffic to the OVS Pod

By default the OVS pod runs in its own network namespace, isolated from both the host platform network and other pods. The application provides two mechanisms to connect traffic into and out of the OVS bridges.

**Host platform access** lets the host operating system communicate directly with the OVS bridge inside the `ovs-agent` pod. When `ovsAgent.hostAccess.enabled` is set to `true`, the application creates a `host-access` NAD backed by a Linux bridge (`ovs0`) that is shared between the host and the pod through a veth pair, attaches a `host0` interface to the OVS pod, and activates bridge failover to avoid duplicate packets. A systemd service, `ovs-access-monitor`, tracks the agent pod's health and switches the bridge membership to the selected SR-IOV PF interface if the pod veth becomes unavailable. This mode requires an SR-IOV PF interface configured in sysinv and an upper ethernet interface with `ovs_access=true` on top of it.

**Pod-to-pod access via bridge CNI** connects application pods to the OVS bridge by pointing both the application pod and the `ovs-agent` pod at the same Linux bridge through a bridge CNI NetworkAttachmentDefinition. This creates a shared Layer 2 segment: traffic from the application pod traverses the Linux bridge into the OVS pod, where it can be forwarded through OVS bridge ports to external networks. Note that pods using SR-IOV resources should prefer connecting directly to the desired interfaces rather than using the bridge CNI method, since direct SR-IOV attachment bypasses the host Linux bridge and delivers near-native I/O performance with lower latency.

### Scaling Across Multiple Nodes

In a multi-node deployment, the OVS Agent runs on every node carrying the `ovs-node=enabled` label. Bridges and ports are distributed across nodes using the `OVSBridge` resource's `nodeSelector` field together with per-node `OVSPort` resources that reference interfaces available on specific hosts.

You can apply additional labels beyond `ovs-node=enabled` to build subgroups of nodes for different topologies. For example, labeling a set of workers with `ovs-role=fronthaul` lets an `OVSBridge` target just those nodes using standard Kubernetes label selector semantics (`matchLabels` and `matchExpressions`). This makes it possible to deploy distinct bridge topologies, such as separate fronthaul and backhaul bridges, to different sets of nodes.

Because each node runs its own independent OVS instance, the `spec.name` of a port can repeat across nodes, but the `OVSPort` resource names in metadata must be unique across the cluster. A common convention is to prefix them with the node name (for example, `worker0-` and `worker1-`) to avoid collisions. The interface names used in `OVSPort` specs must match the `interface` field values configured in the `ovsAgent.networks` Helm override, since those are the Multus interface names that appear inside the OVS Agent pod.

### Conclusion

The OpenvSwitch Operator application brings declarative, Kubernetes-native network switching to StarlingX worker nodes. By describing bridges, ports, and per-node topologies as custom resources, operators gain a repeatable and self-healing way to manage OVS across single-node and multi-node deployments, while still relying on the familiar StarlingX application lifecycle for install, override, and removal.

For the full details, including complete configuration examples for host access, pod access, and multi-node fronthaul topologies, please refer to the [OpenvSwitch Operator Application documentation](https://docs.starlingx.io/node_management/kubernetes/openvswitch-operator-application-overview-db76edcae51b.html) in the StarlingX project documentation.
